> **★★★2026-08-29 実験B(n=3対照実験)で本メモの因果主張は否定された。以下 2026-08-20 の記述は「観測事実」としては正しいが「原因の特定」は誤り。末尾の結論を必ず読むこと。**

**2026-08-20。負荷スイープ(150/200/250/300周/s)で250以上に崩壊が頻発。原因を計測で特定した(と考えた)。**

## 崩壊の様子(適正化枠・frontcatalog 250周/s で再現)
捌けた246/250・取りこぼし1605・p50 1320ms。**にもかかわらず全コンテナの利用率は55〜70%、HPAは1台も増やしていない**(希望台数=現在台数)。

## 追加した計測(bundle-vs-loss2.sh / checkout.js)
- **種類別p50**: checkout.js に `m_product`/`m_cart`/`m_checkout` の Trend を追加(商品/カート/購入を分離)。
- **スロットリング率**(コンテナ別 上位5)、**k6自身のCPU**、**TCP再送/秒** を CSV に追加。
- 列: `k6_cores,tcp_retrans_s,prod_p50,cart_p50,chk_p50,prod_p99,cart_p99,chk_p99,throttled`

## 計測結果=犯人の特定
| 計測 | 値 | 判定 |
|---|---|---|
| 種類別p50 | 商品1209 / カート1177 / **購入1685** ms | 3種とも一様に遅い=入口が詰まっている |
| k6 の CPU | 0.40コア(上限2.0) | **負荷生成側は限界ではない=除外** |
| TCP再送 | 0/秒 | **ネットワーク層でもない=除外** |
| **スロットリング** | **email 48%**, frontend 8-9%, payment 5% | **これが犯人** |

## 機構
- limits(上限)は「**100msごとに quota ぶんだけ**」というカーネルの配給制。email は上限300m=**100msごとに30ms**。
- 仕事はバーストで来るので、**来た瞬間に30msを使い切って残り最大94ms強制停止**。暇な時間が平均を押し下げるため、**平均使用83m(=requests 119mの69.5%)**にしか見えない。
- checkoutはemailを**同期呼び出し**→購入が遅れる→frontendの処理枠が埋まる→商品/カートまで遅くなる(3種一様に遅い理由)。
- **email のCPU総量自体は不足していない**: 0.67mc/周×250 + アイドル ≒216m vs 実測249m。**「量」ではなく「必要な瞬間に使わせてもらえない」問題**。

## ★核心: 利用率が70%に届かない理由は3つあり、全部が「苦しい時ほど下げる」向き
1. **止められている間は使用量として記録されない**(需要は使用量でなく待ち時間に変わる)
2. **上流が詰まると届く仕事が減る**(取りこぼし1605=k6が送れない→emailへの注文が減る)
3. **平均がバーストを隠す**
⇒ **HPAの信号は、システムが助けを必要とするまさにその時に弱くなる。** 「70%に届かないから増やさない」のではなく「詰まっているせいで届かない」=因果が逆転。
⇒ [[hpa-scaling-angle]] の softirq(cgroup外で見えない)に続く **HPAの第2の盲点**。しかもこちらは**遅延に直結**する。過去の「emailを増強したら問題がpayment/adに移動」というモグラ叩きの正体でもある。

## 次の実験(ユーザ承認待ち)
- **B(因果確定, 約1時間)**: limits を requests に比例させた版(例 limits=requests×3)で同条件。**崩壊が消えれば原因確定**。設計指針=「枠の適正化は requests だけでなく limits も含めて行う」。
- **A(相関確認, 約1.7時間)**: 4アーム×250/300×2サイクルを新計測付きで。崩壊した構成ほどスロットリングが大きいかを見る。
- 順序は **B→A** を推奨(原因を除いてから構成比較すれば崩壊レースに邪魔されない)。

# ★★★2026-08-29 実験B 完了 = 仮説は否定(逆向きの結果)
`run-expB.sh`(frontcatalog固定 × 250/300周/s × 上限あり(lx=0)/×10(lx=10) × 3サイクル交互 = 12点)。資産: `results-expB-limits.csv` / `timeline-expB-limits.csv` / `expB-limits.log`。

## 結果(取りこぼし 平均±sd, n=3)
| 負荷 | 上限あり | 上限×10 |
|---|---|---|
| 250周/s | 1358±1271 (p50 126ms, 絞り24%) | 2733±2424 (p50 2292ms, 絞り0%) |
| **300周/s** | **34±52 (p50 207ms, 絞り80%)** | **13851±12385 (p50 3339ms, 絞り1%)** |
同一サイクル同士のペア比較で **6組中5組で「上限なし」が悪い**。300周/sでは平均400倍の差。

## ★決定的: 絞り率で並べると逆相関
絞り94%→取りこぼし8 / 93%→94 / 52%→0(**最も絞られた3回が最も健全**)。絞り0-4%の回に 3576, 4623, 17367, 24097 が並ぶ。**絞り率と取りこぼしの相関 r = −0.39**。
⇒ **スロットリングは崩壊の原因ではない。** つまみ自体は完全に効いていた(×10で絞り0-2%、対照26-94%)ので、操作の失敗ではなく仮説の否定。

## 訂正される主張
- ❌「250-300周/sの崩壊の犯人=email 48%のスロットリング」= **相関を因果と取り違えた誤判定**。
- ❌「設計指針=枠の適正化は requests だけでなく limits も含めて(緩めて)行う」= **撤回。limits は現状維持が正解。**
- ⭕ **上限は保護装置として働いている**。外すと frontend が上限10.8コアまで使えるようになり16コアのノードで奪い合い→悪化(機構は仮説だが向きは実証)。
- ⭕ 残る正しい観測: 絞られている間は使用量に現れずHPAに見えない、平均がバーストを隠す、という**計測上の性質**自体は事実。ただし**それが崩壊を引き起こすわけではない**。

## ★崩壊の正体(現時点の最有力)= ノード容量限界付近の双安定
崩壊は上限と無関係に両条件でランダムに発生。300周/sでは予約枠13-14コア+Pending 2-4台で**16コアのノードが満杯**。[[hpa-scaling-angle]] の u480 双安定と同型。**単一のつまみで消せる類の現象ではない。**

## ⇒ 次の一手 = マルチノード化(結論が2方向から一致)
- 縦軸(SLOを満たせる最大負荷÷予約コア)を測るには崩壊しない範囲で負荷を上げ切る必要がある → ノードを増やすしかない。
- 同時に、分離構成の通信が本物のNIC/オーバーレイを通るようになり **得が現実サイズになる**(単一ノードでは分離側もloopbackで終わるため得が過小=ICTer批判への答えにもなる)。
- **1つの作業で2つの問題が解ける。** [[coloc-bundling-decision-rule]] の効率カーブ測定はマルチノード化後に実施する。

# ★★★2026-08-30 崩壊の原因を特定 = 「2つの別々の原因」だった
実験Bで否定された後、`PRESCALE`(負荷開始前に全Deploymentを何台にしておくか。既定2)を振って切り分けた。資産: `results-prescale.csv`(300周/s) / `results-prescale250.csv`(250周/s) と対応する `timeline-*` `prescale*.log`。

## 結論の表
| 負荷 | 崩壊の原因 | 対処 |
|---|---|---|
| **250周/s** | **ウォームアップ中にHPAが必要台数へ増やしきれない(出遅れ)** | **開始台数 2→3台 で解決(実証済)** |
| **300周/s** | **ノードの容量不足**(予約枠14コア台+Pending 2-7台。16コアの物理天井) | 開始台数では解決不能 → **マルチノード化** |

## ★250周/s: 開始台数だけを変えた対照(frontcatalog, 枠適正化済, 上限は現状維持)
| | 開始2台 (n=5) | **開始3台 (n=3)** |
|---|---|---|
| 取りこぼし | 0/1200/1555/2058/2519 (平均1466±960) | **0/0/0 (0±0)** |
| p50 | 平均554ms(最大2378) | **平均17ms(15/18/17)** |
| 崩壊(>1000)した回 | **4/5** | **0/3** |
| 落ち着いた後の予約枠 | 12.32コア | 12.97コア |
⇒ **崩壊は完全に消えた。しかも定常状態の予約枠はほぼ同じ=効率の指標を汚さずに崩壊だけ除去できる。**

## 機構(確定)
2台から始めると全サービスが同時に3台目を要求 → 増加が間に合う前に行列が育つ → 取りこぼしでサービスに届く仕事が減る → 利用率が下がる → HPAが「増やす必要なし」と判断 → **低い枝に固定**([[hpa-scaling-angle]] の双安定と同一)。
※ 8/20に書いた「HPAの信号は助けが要る時に弱くなる」という**機構の記述は正しかった**。誤っていたのは引き金をスロットリングだと特定した点だけ。

## ★300周/s では PRESCALE=3 が逆効果(n=3)
取りこぼし 13726/82/13(平均4607±7897, 崩壊1/3)、Pending 2.7台→**4.7台**。開始3台=12.42コアを先に予約するとHPAが動かす余地が3コアも残らず、増やしたいサービスがPendingのまま空回り(recommendationは2台に減らされた)。**PRESCALEの上限は3**(4台=16.56コアはノード16コアに載らない)。

## 否定された仮説(この日だけで3つ)
1. スロットリングが原因 → 実験Bで否定(r=−0.39)
2. **「束ねるとPodが大きくなり載せにくい=詰め込み損」→ 否定。** 300周/sのfrontend Pod の Pending時間率は normal(1077m)71% > frontcart(1438m)75% ≈ frontreco(1819m)67% > **frontcatalog(1739m)42%** で、大きさと逆。Pod内で見た r=+0.88 は「大きいPod=熱いサービス=増やそうとする回数が多い」という交絡だった。
3. Ready落ち/Pending が崩壊の原因 → いずれも逆相関(崩壊した回ほど少ない)=結果であって原因ではない

## ⇒ 実務的な帰結
- **250周/s までは PRESCALE=3 で安定測定できる土俵ができた。**効率カーブ測定はここまでなら可能。
- **250周/s以下では Pending は14回中1回のみ・予約枠最大13.33コア(空き1.7コア)** = ノードは満杯ではない。
- 300周/s以上を測るにはノードを増やすしかない。
