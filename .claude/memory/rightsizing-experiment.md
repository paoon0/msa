**ユーザ発案「つまみ(枠)は調整できる方がいいのでは」から実施。** 資産: `km2/experiments/summer2026/` の `rightsize.py`(テーブル生成) / `apply_rightsize.py` / `reserved.py` / `rightsize-requests.csv` / `results-rightsized.csv` / `timeline-rightsized.csv`。

## 適正化の規則(これ1つ)
**枠_s = (アイドル分_s + 1周あたりCPU_s × k) / 0.7**、k=1台に担当させる負荷[周/秒]=100。
- 入力は [[perservice-utilization-curves]] の1台固定測定から直線回帰(絞り>5%の点は除外)。**limits は変更しない**(絞りの人工影響を避ける)。
- 適正化前は全サービスが1.2〜3.4倍過大で不揃い。reco 1200→742m / currency 800→523 / checkout 800→321 / cart 560→361 / ad 300→69。**frontend 1000→1077m・catalog 600→662m だけは上がる**(この2つは枠がきつかった=だから最初に70%へ届いていた)。

## ★結果1: 適正化そのものの効果(200周/s, 4アーム×3サイクル)
| | 適正化前 | 適正化後 |
|---|---|---|
| 予約枠合計(台数から計算) | 12.48コア | **9.98コア(−20%)** |
| p50 | 9〜406ms(乱高下) | **8〜10ms(全12回)** |
| 取りこぼし | 502 | **0** |
| Pod数 | 17〜19 | 24〜26(小さいPodが多数) |
p50の乱高下は待ち行列の閾値現象(応答≒1/(1−利用率): 70%で3.3倍, 90%で10倍)。適正化で毎回"崖の手前"に固定された。

## ★★結果2: 粒度損は消えず「移動」した
適正化後200周/sの必要台数: frontend2・catalog2・reco2・**cart3**(枠を560→361mに絞った結果 cart が最も熱いサービスに転じた)。
| 束ね | 適正化前の損 | 適正化後の損 |
|---|---|---|
| front+catalog | +0.40 | **0.00 ±0.00 (3/3で完全ゼロ)** |
| front+reco | +1.20 | +0.61 (3回中1回のみ) |
| front+cart | +0.36 | **+1.08 ±0.00 (最悪に転落)** |
- frontcartの損 = cart(3台)に引きずられ **frontend(枠1077m)が2→3台** = 1.077コア。実測+1.08と一致。
- **設計則の訂正: 「枠の大きい相方を避けよ」は誤り。正しくは「必要台数が一致する相手と束ねよ」。損=(引きずられて余分に立った側の枠)×(余分な台数)。** 枠の大小は"誰が損を被るか"を決めるだけ。熱い/冷たいの役割が入れ替わっても式は当たった=**枠の与え方に依存しない**強い証拠。
- **frontend+productcatalog は適正化の前後どちらでも損が最小**(後は3/3で完全ゼロ)かつ通信最重量 = 両軸一致の唯一の組。

## ★★★理論の訂正(2026-08-20, 重要)
一度「アイドル分の割合 f が違うので、基準負荷から離れると高さが再びズレる」と説明したが**誤り**。
u_s(x)/0.7 = f + (1−f)(x/k) を1に解くと **x = k(f に依らない)**。⇒ **適正化した枠では、どのサービスも「1台あたり k 周/秒」でちょうど70%に達する = 必要台数 ⌈L/k⌉ が全サービス同一 = 理論上どの負荷でも粒度損ゼロ**。
f が効くのは「70%からどれだけ上振れするか」(2k負荷で 2−f 倍)だけ。
⇒ **残った損(cart +1.08)の正体は f ではなく「適正化に使った需要予測(アイドル+1周CPU×L)の誤差」**。
> **粒度損 = 需要予測の誤差 × 枠。** 完璧に測れれば損はゼロにできるが、実運用で完璧な予測は不可能なので損は残る。
これは主張として強い(「right-sizing すれば解決」への反論になる)。**真に消せない損は需要のズレ(混合ワークロード)から来るはず=実験2の主題**。

## 測定の規律(前回の失敗から確立)
**損と得は別の負荷帯で測る。混ぜると壊れる。**
- **安全域(全サービス≤70%)で損を測る**: 全構成が満額捌けるので「同じ仕事にいくら資源を使ったか」が正しく比較できる。
- **崖の近くで得を測る**: 束ねの利得は「崖が右にずれる」形で出る。ただし**1点比較は不可**(崩壊レース)。負荷を刻んで**崖の位置**を3回以上測る。
- **崩壊の指紋(260周/s 1回目で観測)**: ノードは16コア中7.8〜9.0しか使っていない=ハード限界ではない。詰まると k6 側で送れなくなり(取りこぼし10958)アプリに届く仕事が減る→下流が暇に見える→**HPAが増やさない/むしろ減らす**(normal の reco が 200→260周/sで 2台→1台、frontcatalog の ad が 3→1台)=悪循環。**「効率=捌けた÷枠」は崩壊した構成ほど良く見える壊れた指標**になる。

## 実装上の罠(踏んだもの)
- **`python3 - <<'PY'` はheredocが標準入力を占有**しパイプのJSONが届かない→時系列0行。集計pythonは別ファイルに。
- Prometheusの `requests * on(pod) group_left kube_pod_status_phase == 1` は `==1` の位置で別物(3.00固定)、括弧で閉じても空(0.00)→ **Pod実体から数える `reserved.py` に変更**。
- 枠を絞ると立ち上がりにHPAが暴走(ad が7台/22%)。対策=開始台数 PRESCALE=2、HPA behavior(増やす様子見30s/減らす60s。既定の減らす300sだと増えすぎが計測窓に残る)。
- frontcart 3サイクル目は k6 summary 回収失敗で n=2。

## ★実験1=負荷スイープ完了(2026-08-20, 150/200/250/300周/s × 4アーム × 2サイクル, `results-loadsweep.csv`)
**安全域(150-200)の結論=信頼できる:**
- **150周/s: 4構成すべてが完全に同一(動作枠8.23コア・取りこぼし0・p50 7〜9ms、2サイクルとも)= 粒度損ゼロ。理論の予測が的中。**
- 200周/s: normal 9.71 / frontcatalog 9.61 / **frontreco 11.70(両サイクルとも+2.0)** / frontcart 10.73。基準ぴったりの負荷でも**予測誤差の分だけ損が出る**(reco が最大)。
**不安定域(250以上)=単純比較は不可:** 取りこぼし合計 frontcatalog 19525 > normal 4811 > frontreco 4569 > frontcart 2852。同じ構成が回によって崩壊/健全に分かれる(frontcatalog 300は16267→0)。
**Ready落ち(プローブ失敗で一時的にサービスから外れる)は構成でなく負荷で決まる**(300周/sで全構成13〜31%)=主犯ではない。
**崩壊の正体は別途特定 → [[hpa-throttling-blindspot]]** (CPU上限によるスロットリング。全コンテナ55-70%でHPA静止のまま詰まる)。
