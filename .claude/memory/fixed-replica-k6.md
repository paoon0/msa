**資産: `km2/experiments/summer2026/results-fixed4.csv`(36点)/ `timeline-fixed4.csv` / `fixed4.log`。実行は `bundle-vs-loss2.sh` に 2026-09-09 追加した3つのつまみ。**

## 何をした実験か
HPA を切って**全 Deployment を4台に固定**し、「オートスケーラが何台選んだか」という交絡を外して通信の得だけを見た。
- アーム: `normal`(分離) / `frontrecocatalog`(front3 = frontend+reco+catalog 同居、cart は外) / **`mega`(全部入り、新規追加)**
- 枠: **requests を全コンテナ一律 150m、limits はマニフェスト据え置き**(2026-07-14 `latency-breakdown/fixed-replicas.sh` の規則を踏襲)。
  → 予約が3アームとも **6.30 コア**(4台×10コンテナ×150m + redis 300m)で**完全一致**。limits は3アームともサービス単位で同一と確認済み(frontend 1600m/reco 1600m/catalog 1000m…)。
- 負荷: k6 開ループ、購入型のみ 150/200/250/300 周/s、ウォーム90秒+計測120秒、3サイクル。

## スクリプトに足したつまみ(`bundle-vs-loss2.sh`)
- `FIXED_REPLICAS=N` … HPA を作らず全 Deployment を N 台に固定(redis-cart は1)
- `UNIFORM_REQ_M=150` … requests を一律化(limits は触らない)
- `mega` アーム … `km2/all/all.yaml`。**`MEGA_REDIS=shared`(既定)で redis を Pod の外に出す**。複数台にすると Pod内 redis が台数分でき、カートが割れて1周の仕事量が他アームと変わるため。`extract_redis.py` で redis-cart を切り出し、megapod から redis コンテナを JSON patch で除去し `REDIS_ADDR=redis-cart:6379` に向ける。

## ★結果(3サイクル平均±sd。全36点で取りこぼし0・失敗0・実測=目標)
**softirq [ms/周]**: 150周/s normal 3.034±0.028 / front3 2.340±0.006(**−22.9%**) / mega 1.499±0.029(**−50.6%**)。
300周/s では front3 −18.3% / mega −42.9% と削減率がやや縮む(mega の per-周 softirq が 1.50→1.68 と負荷とともに増える。normal は 2.91〜3.03 でフラット)。
**sd が 0.006〜0.075 に対し差は 0.5〜1.5 = sd の10倍以上**で決定的。

**実CPU時間 [コア秒/1万周](k6分を除く)**: mega は 150/200/250 で **−7.9〜−10.4%**、front3 は 150/200 で −2.4%、250/300 では ±1% 以内。300周/s は normal のばらつきが急増(±16.8)。

**p50 [ms]**: 300周/s で normal 23/79/64(平均55)に対し front3 19/21/20・mega 18/17/16。**高負荷では分離だけが暴れる**。250周/s でも normal 12/18/14 vs 束ね 10〜12。

## 位置づけ
7月の locust 閉ループ・HPA下の値(mega −52%、front系 −9〜−15%)を、**開ループ・台数固定・予約完全一致**という交絡のない条件で再現した。「束ねの得 = HPA が台数を1台減らしたから」ではないことの直接証拠になる。

## ★★崖の特定(2026-09-10 完了。350/400/450 を6サイクル=54点。`results-fixed4b.csv`)
**取りこぼしゼロを6サイクル維持できる最大レート = normal 300 / front3 350(+17%) / mega 400(+33%)周/s。**
崩れた後の到達上限は normal 361.6 / front3 439.5(+21.5%) / mega 437.4(+20.9%)。
- 350: **12サイクルに増やしたら normal は 3/12**(6回時点では4/6成功に見えた=6回では足りない。後半6回は全滅、熱ドリフトは無し)。front3・mega は **12/12 完璧**(実測sd 0.0、p50中央 72/52ms)
- 400: **normal 0/12**(353.8±23.6, p50中央2898ms) / front3 1/12(399.5±0.4, 落ちても15〜163=分離の1/100) / **mega 10/12ゼロ(399.9±0.1)**
- softirq 12サイクル: 350 = 2.685±0.084 / 2.180±0.043(−18.8%) / 1.571±0.056(−41.5%)、400 = 2.588±0.220 / 1.888±0.066(−27.1%) / 1.396±0.043(−46.1%)
- ★休憩(アーム間60s/サイクル間300s)で熱ドリフト無し = 前半6と後半6のノードCPU差は −0.24〜+0.36コア
- 450: 全滅(normal 359.6±22.9 / front3 439.5±5.5 / mega 437.4±1.6)

★**分離には約360周/sの硬い天井**があり、400要求でも450要求でも捌くのは 361.6→359.6 と同じ。そのとき**ノードCPUは13.0〜13.5コア(/16)で2.5〜3コア余らせたまま**止まる。mega は15.1コアまで使って437まで伸びる。
⇒ **分離の限界はCPU不足でなく「ネットワーク往復の待ちでCPUを使い切る前に詰まる」**。co-loc はこの待ちを外し、同じ台数・同じ枠のまま余っていた2〜3コアを使えるようにする。

★**front3 と mega はスループットでは並ぶ**(439.5 vs 437.4)。3サービス束ねた時点で得はほぼ取り切っている。mega が優るのは安定域(400でゼロ5/6 vs 1/6)・遅延(350でp50 52 vs 70ms)・softirq のみ。

★**500周/s(cyc4, 1回)= 3アームとも崩壊**: normal 348.4(落18187, p50 3416ms, 12.1コア) / front3 424.8(9025, 1973ms, 14.8コア) / mega 434.5(7857, 1839ms, 15.2コア)。
**Ready落ちが全アームで発生**: normal=reco 3/4 / front3=**email 3/4**(recoは束ねの中なので次に弱いemailへ移った) / mega=**megapod 3/4 = 1台で10サービス分の容量が同時消失**。
⇒ 効率と安定域では mega が勝つが、**失敗時の被害範囲も最大**。「効率 vs 堅牢性」の実データ。

## ★★プローブ対照実験(2026-09-11完了・査読対策の本丸。`results-probe5.csv`)
**問い**: 分離の容量律速は reco の readiness プローブ既定値(timeoutSeconds=1)のせいではないか(=ベースラインの設定不備を測っているだけ、という査読指摘への備え)。
**方法**: reco の readiness/liveness を **timeoutSeconds 1→5** に patch(マニフェスト無編集。`PROBE_TIMEOUT` つまみを bundle-vs-loss2.sh に追加、strategic merge patch でコンテナ名一致=reco だけに当たる)。分離 350/400周/s を **12サイクル**、front3 は6サイクル。他条件は 4台固定・150m一律と同一。

**★結果=回復しない(主張は守られた)**
| 負荷 | timeout=1(12cyc) | timeout=5(12cyc) | p |
|---|---|---|---|
| 350 | 0落ち 3/12、実測344.6±9.4 | 6/12、実測**335.3±23.8**(平均は悪化・sdは倍) | 0.400 |
| 400 | 0/12、353.8±23.6 | 1/12、361.6±26.1 | 1.000 |
front3 は不変(350で6/6・350.0±0.0、400で399.9±0.1)。**容量差は解消しない。**

**★機構の確証**: Ready落ちと崩壊の対応は24点で例外ゼロ。**Ready落ちあり13点は全て崩壊(取りこぼし中央値4,669)、Ready落ちなし11点中7点が完全成功**(cyc3の400周/sは400.0を取りこぼし0)。
**★timeout=5 でも Ready落ちは13/24で発生**(reco 8回・**触っていない email 7回**=障害が移動)。過負荷時の応答は5秒すら超える ⇒ **プローブ失敗は容量不足の症状であって原因ではない**。

## 実装上の罠(2026-09-11)
- patch ループで変数 `c` を使い、外側のサイクル番号と衝突 → CSVのcycle列が "recommendationservice" に化けた(測定値は無傷・行順で復元可)。`pc` に改名して修正済み。
- **rollout status が先に返り、Ready 3/4 のまま負荷開始して1サイクル無効化**。全Deploymentが所定台数Readyになるまで待つガードを deploy() に追加済み(最大420秒)。
- 実行中のシェルスクリプトは編集しないこと(bashが逐次読みするため壊れる)。

## 実験の休憩つまみ(2026-09-10 追加)
`REST_ARM` / `REST_CYCLE`[秒] … アーム間・サイクル間に無負荷の休憩を挟む。長時間連続で回すと熱でCPU周波数が落ち、後半サイクルだけCPU時間が増える系統誤差が入るため。今回は 60秒 / 300秒。
