## ★★★主結果: 束ねの「得」を予約CPUで初めて直接観測
200周/s、分離のfrontendは**3サイクルすべてで3台必要**。対して:
| 束ね | 束ねPodの台数(3回) | 正味[コア] | 性格 |
|---|---|---|---|
| **front+catalog** | **2, 2, 2** | **−1.08 ×3回** | **決定的な節約** |
| front+reco | 2, 3, 2 | −1.82 / +0.74 / −1.08 (平均−0.72) | 3回中2回節約 |
| front+cart | 3, 3, 3 | 0.00 ×3回 | 影響なし |
p50も同方向: normal 401/10/73ms に対し frontcatalog 9/9/10ms。
**機構(利用率データで裏取り)**: 束ねたfrontendコンテナは2台で**70%ちょうど**、分離frontendは3台で50%(=2台なら約75%)。**同居でfrontendのCPUが5-7ポイント下がり、70%の崖を割らずに済む**。catalogとrecoはどちらも商品閲覧パス上にあるのでfrontendのホットパスからホップが1つ消える。cartはカート操作パスで自分も3台要るため効果なし。
**catalogとrecoの差=信頼性**: catalogは自分の利用率が64%で余裕があるが、recoは71%と崖の上にいるため時々自分の都合でPodを3台に引き上げる。

## ★粒度損は「台数が揃わない負荷帯」でしか出ない(再確認)
150周/s: 4構成すべて8.60コアで完全一致(14回連続)。250周/s: 健全な回はすべて8.53コア。**損が出るのは200周/sだけ**=1台あたり100周/秒=70%の崖ちょうど。
帰属ベースの粒度損(相方が自分に不要な台数まで立たされた分)は **frontreco 200周/sで1/3回だけ +0.74**、他はすべてゼロ。

## ★★解析方法の訂正(重要な教訓)
**「関係4サービスの予約枠の合計を分離と引き算」する方法は誤り。** catalog/reco/cartは200周/sで70%の崖に並んでおり、束ねと無関係に2↔3台を行き来する。そのコイン投げが差に混ざり、「frontcartの損 +1.08」のような**実際にはrecoの1台増だけが理由の数字**を生んだ(セッション中に一度そう報告して撤回)。
⇒ **正しくは帰属で数える**: 束ねPodの台数と、各メンバーが単独で必要だった台数を比べ、束ねに入っているサービスだけを価格付けする。束ねに入っていないサービスは一切数えない。`loss_attributed.py`。

## ★第3軸(堅牢性)の示唆
250周/sの p50: frontcatalog **17/1095/946ms**(3回中2回劣化)、frontreco 34/34/13ms(3回とも健全)、frontcart 374/26/156ms、normal 19/28/16ms。予約コアは全構成同じ8.53なのに**遅延だけが構成で大きく違う**。
⇒ **front+catalogは効率で最良・安定性で最弱**の可能性。ただし各アーム3回では確定できない。要=4アーム同回数の堅牢性実験([[coloc-bundling-decision-rule]]の第3軸)。

# ★★★2026-09-02 目的関数を確定(ユーザ判断)= 実CPU時間 + 取りこぼし
**予約枠(requests×台数)を主指標から外す。** 理由=requests は我々が決めたつまみなので、値を変えれば結論が変わる。実CPU時間は物理量、取りこぼしはSLO。どちらもつまみに依存しない。
**粒度損を独立項として追わない(ユーザ判断)。** 「どれだけエコにパフォーマンスを出せるか」が主題であり、**余分な台数のコストは最終的なCPU時間に自動的に含まれる**(アイドル分として)。二重計上は不要。

## 目的関数(確定版)
> **同じ仕事(N回のトランザクション)を、SLOを満たしながら、何秒のCPU時間で処理できるか。**
> 束ねるべき組 = この値を最小にする組。
- SLO = 取りこぼしゼロ(必要なら p50 上限も)
- **比較は取りこぼしゼロの負荷帯でのみ行う**。取りこぼしが出た構成はその負荷を捌けていないので比較対象外(詰まると待ち行列でCPUを余計に使い、指標が壊れる)
- 容量 = 取りこぼしが出始める負荷
- 従来の項目はすべてここに吸収される: softirq削減→CPU時間減、粒度損→余分Podのアイドル分、Pod固定費→同、容量→取りこぼし

## 用語の注意
- **周** = 負荷ツールの1ループ = 利用者1人分の買い物(商品閲覧→カート→購入、実HTTPは4本)。負荷は 周/秒。
- **サイクル** = 実験全体の1巡(4構成×3負荷=12測定)。混同注意。論文では「周」を「トランザクション」等に言い換える。

| 150 | **frontcatalog** | **1213s** | **337.0s** | **−2.7%** | 0,0,0 |
| 150 | frontreco | 1233s | 342.4s | −1.2% | 0,0,0 |
| 150 | frontcart | 1231s | 342.0s | −1.3% | 0,0,0 |

## ★粒度損は今回0件(直接判定で確定)
ユーザ発案の判定法=**台数が増えた瞬間の各コンテナの利用率を見る**。片方が70%未満のまま引き上げられていれば粒度損。
結果: 台数が決まる2→3台の増加は**全回で両コンテナとも70%超**=引きずられていない。唯一の例外は frontcart cyc3 @150 の 1→2台(cart 112% / frontend 53%)だが、最終台数は分離と同じ2台なので余分な資源にはなっていない。
⇒ **レポートの「frontreco +0.74コアの損」は撤回。粒度損の観測は0件。** 間接判定(分離構成の台数を借りる)は基準自体がコイン投げなので弱い。
## 副産物: 台数はウォームアップ中(31-107秒)に決まり、その後固定される
増加時の利用率は80-120%(立ち上がりの過渡値)。落ち着いた後は reco が2台で68%・3台で55%と**どちらもHPA的に安定**(3台から2台に減らすと82%で目標超のため戻らない)。⇒ 台数は必要量でなく**立ち上がりの軌跡**で決まる=双安定と同型。

# ★★★2026-09-02 損と得で指標を分ける(ユーザ判断)
## 経緯
混合ワークロード(購入型100固定 + 閲覧型0/100/200/300)で**粒度損の直接観測に初めて成功**。
束ねPodの増加15回中5回で、片方が70%未満のまま引き上げられた(9/1実験では0件)。
★frontcart は**閲覧比率で損の向きが逆転**: 閲覧0では cart 79-80% が frontend 57-67% を引き上げ、閲覧300では frontend 86-92% が cart 64-67% を引き上げる。サイクル1・2の両方で再現。
★frontcatalog / frontrecocatalog は全増加で両コンテナとも70%超 = **損ゼロ**(閲覧経路同士なので比率によらず同時に熱くなる)。

## ★ユーザ指摘 = 「CPU時間に現れなければ損とは言えない」→ 数字で確認、正しかった
引きずられが起きた5測定のCPU時間の差は **−16.0% / −2.4% / +0.1% / +0.9% / +9.2%** で**方向すら一定しない**(=ノイズ)。同じ測定の予約枠の差は **+17.6% / +29.7% / +3.2% / −2.5%**。
理由: **粒度損は「確保するが使わない」現象。** 余分な1台の実消費はアイドル分だけ。
| | 確保する枠(240秒) | 実消費(アイドル) |
|---|---|---|
| frontend | 258.5 コア秒 | **36.7 コア秒** (全体1500の2.4%) |
| cartservice | 86.6 | 9.8 |
| recommendation | 178.1 | 9.4 |
⇒ **CPU時間を主指標にすると粒度損はほぼ観測できない。** 指標の欠陥ではなく、**この環境では粒度損が実際にコストになっていない**(ノードに空きがあるので余分なPodが場所を占めても誰も困らない)。

## ★決定(ユーザ選択=案1)
- **得** = 実CPU時間 + 取りこぼし。物理量でつまみ非依存。**主指標**
- **損** = 予約枠(コア秒)。**つまみ(requests)依存であることを明記した上で、損の指標として明示的に使う**
- 主張は条件付きにする: 「**クラスタが混んでいて予約枠が制約になる状況では損になる**」。単一ノードで1アプリしか動かしていない現環境ではその状況が作れていない
- 不採用にした案: (2)他ワークロードを載せてノードを混ませる=研究として最強だが実験設計が変わる / (3)粒度損を主張から外す

## 計測基盤の変更(この日)
- **CPU時間**: `rate[200s]×240` → **`increase(node_cpu_seconds_total[MEAS s])`**。窓と平均区間のずれ(最初の40秒を外挿)を解消。列 `node_cpu_sec`
- **softirq**: 購入型の周数で割るのをやめ絶対値(`softirq_cpu_sec`)に。閲覧型を混ぜると分母が足りず解釈が破綻するため(実測: HTTP1本あたりに直すと0.67-0.75でほぼ一定=通信効率は悪化していなかった)
- **予約枠の時間積分**: `sample_hpa.py` が15秒ごとに名前空間全体の予約枠(Running/Pending)を記録(取得は既存の再利用で追加コスト0)。`window_reserved.py` が窓の積分を計算 → 列 `reserved_core_sec` / `pending_core_sec` / `reserved_avg_cores` / `n_samples`。**使ったCPU秒と同じ単位なので「使用率=使った÷確保した」が出せる**(スモークで63.3%)
