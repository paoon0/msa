## 0. 全体像

このスクリプトは、**「分離構成 (1 Pod 1 サービス) で、全サービスを 1 台または 2 台に固定し、購入と閲覧を混ぜた負荷をかけたとき、各サービスのコンテナが何ミリコアの CPU を使うか」を、17 種類の配合 × 2 通りの台数 × 6 サイクル分、自動で測って CSV に書く**もの。

```
measure-mix-cpu.sh
 ├ 設定を読む (28–76)
 ├ ログの記録を始める (78–79)
 └ サイクル 1〜6 (192–201)
     └ 台数ブロック 1台 / 2台 (順番はサイクルで入れ替え)
         ├ deploy()  … 構成を立て直す (109–145)
         │    ├ kubectl apply / scale / set resources
         │    ├ grpc_lb_patch.py → kubectl patch (振り分け)
         │    └ 慣らし負荷 (k6 を 180 秒、結果は捨てる)
         └ 17 点をランダムな順に
              ├ cool_down() … CPU 温度 70℃ 以下まで待つ (151–156)
              ├ run_point() … 1 点を測る (159–189)
              │    ├ k6 の Job を起動 (checkout.js が負荷をかける)
              │    ├ 240 秒 + 15 秒待つ
              │    ├ Prometheus に 9 本問い合わせ (curl)
              │    ├ k6 のログから集計を回収
              │    └ _write_mixpoint.py → CSV 2 本に追記
              └ 60 秒休む
 解析は別に手で実行: analyze_rho2.py → analysis-rho2.txt
```

【事実】実際の実行 (`data/results-mix-cpu2.log`) を数えた結果:
- START 行が 1 回 (途中でやり直していない)
- 測定点の開始が 204 回 (= 17 点 × 2 台数 × 6 サイクル)
- deploy が 12 回 (= 6 サイクル × 2 台数)
- CSV に書かれた点は 203 点

## 5. 結果の保存先と、集計・分析の流れ

```
k6 (Pod の中)        ─┐ 集計 JSON を標準出力へ (checkout.js:129–165)
Prometheus          ─┤ 9 本の問い合わせ結果 (JSON)
                      ↓ 環境変数で受け渡し (185–187)
_write_mixpoint.py
  ├→ results-mix-cpu2.csv          1 行 = 1 点 × 1 サービス (Pod は合計)   ← 主データ
  └→ results-mix-cpu2-series.csv   1 行 = 1 点 × 1 サービス × 10 秒
画面出力 → tee → results-mix-cpu2.log  (78 行。設定・各点の要約・異常の記録)
                      ↓ (手で実行)
analysis/analyze_rho2.py → analysis/analysis-rho2.txt   (ρ・区間・感度)
```

- 【事実】CSV は**追記** (`_write_mixpoint.py:86` の `open(out, 'a')`)。ファイルが空のときだけ見出しの行を書く (81, 88–89)。同じファイル名で 2 回実行すると、**2 回分が 1 つの CSV に混ざる**。
- 【事実】解析はこのスクリプトからは呼ばれない。`analyze_rho2.py` を別に実行する (`analyze_rho2.py:12`)。
- 【事実】主データの列の意味:
  - `usage_mc`: CPU 使用量 [ミリコア]
  - `req_mc` / `lim_mc`: requests / limits の Pod 合計
  - `throttle_pct`: 絞りの割合 [%] (Pod の中で最大のもの)
  - `buy_dropped_win` / `view_dropped_win`: 計測窓の中での取りこぼし [周]
  - `node_cores`: ノード全体の CPU [コア]
  - `freq_ghz`: CPU 周波数 [GHz]
  - `temp_max_c`: 温度 [℃]

## 6. 呼び出される別のプログラム

### (a) `k6/k6-job.yaml` と `k6/checkout.js` (負荷)
- 【事実】Job の雛形。`k6-job.yaml:28–33` の `__RATE__` などを、スクリプトの 106 行の `sed` で埋める。Pod は `k6 run` が終わったあと `sleep 300` で 5 分間生き続ける (`:25`)。終わった直後にログを回収できるようにするため。
- 【事実】`checkout.js:57–86`: 購入と閲覧を別々のシナリオにして、どちらも**開ループ** (`constant-arrival-rate`) で流す。開ループ = 応答が遅れても毎秒決まった数の周を開始し続ける方式。開始できなかった分は「取りこぼし」になる。
- 【事実】`checkout.js:88, 91, 119`: 起動時刻を記録し、そこから WARMUP 秒が過ぎたあとに**開始した**周だけを数える。
- 【事実】`checkout.js:136, 138`: 取りこぼし = 目標レート × 計測秒数 − 窓の中で開始できた周の数
- 【事実】`k6-job.yaml:24`: イメージは `grafana/k6:latest`。「最新版」という指定なので、実行した日によって中身が変わり得る。

### (b) `scripts/grpc_lb_patch.py` (振り分け)
- 【事実】クラスタの中身を変える処理を自分では実行しない。**kubectl のコマンドを文字として出力するだけ**で、実行するのはシェル側 (132 行)。
- 【事実】やること:
  1. 各コンテナの `*_SERVICE_ADDR` (呼ぶ相手の住所) を見る。`localhost` 宛て (同居) は触らない
  2. 呼ばれる側の Service ごとに headless 版 `<名前>-hl` を作る。headless = 仲介せずに全 Pod の IP を直接返す Service
  3. 呼ぶ側の住所を `-hl` のほうに書き換え、`GRPC_LB_POLICY=round_robin` (順番に振り分ける) を足す
  4. 呼ぶ側 (frontend・checkout・reco) のイメージを、振り分け対応版に差し替える。`imagePullPolicy: Always` で毎回イメージを取り直す
- 【事実】ログでは「gRPC負荷分散: checkoutservice (checkout+img)」など 3 行が出ていて、3 つの Deployment に当たったことが分かる。
- 【事実】1 台の点では振り分ける相手が 1 台しかいないので、振り分けの効果はない。イメージの差し替えは 1 台・2 台の両方に入るので、両者の条件は揃っている。

### (c) `scripts/_write_mixpoint.py` (CSV への書き出し)
- 【事実】`dep_of()` (46–49): Pod 名 `frontend-7f9c…-x2kqp` の末尾を削って Deployment 名にする。2 台のときは同じ Deployment の 2 つの Pod の CPU を足す (70–77)。
- 【事実】k6 の集計から、捌けたレート (`started ÷ 180`)・取りこぼし・p50/p99 を取り出す (53–64)。
- 【事実】絞りが 5% を超えたサービスがあれば、ログに「!! 絞り 5% 超」と出す (117–120)。この時点では除外しない。除外するのは解析側。

### (d) `analysis/analyze_rho2.py` (解析)
- 【事実】除外 (54–57, 62–63) → サービス・台数ごとに `D = c + β·buy + ν·view` を最小二乗 (38–44, 73–79) → ρ = ν/β → サイクル単位のブートストラップで区間 (82–88)。

## 7. 妥当性・再現性に関わる重要な処理

| # | 処理 | 場所 | なぜ重要か |
|---|---|---|---|
| ① | **計測窓の時刻** | 166–170 | `t_end = t_run + 60 + 180`。Prometheus は `[t_beg+10, t_end−10]` の 160 秒を平均する (`rate(...[160s])` を `t_q = t_end − 10` で評価)。k6 の窓の両端を 10 秒ずつ内側に削っている。【推測】k6 の起動時刻と `t_run` のずれは数秒で、10 秒の削りで吸収できているはずだが、**ずれの実測値はない** |
| ② | **CPU の定義** | 172, 174 | `container_cpu_usage_seconds_total` = コンテナの cgroup の CPU 時間。`container!=""`, `container!="POD"` で、Pod 全体の合計の系列を除いて二重計上を防いでいる。softirq の多くは cgroup の外なので、**この値に通信処理の CPU はあまり入らない** (【推測】どの程度入るかは測っていない) |
| ③ | **回収に失敗した点の扱い** | 184 | k6 の集計が取れないと、**CSV に書かずに次の点へ進む**。解析側からは「点が無い」ようにしか見えない。【事実】cyc2・1 台・b100v75 がこれに当たり (ログ 934 行)、解析の出力は「未回収 0 件」と報告している |
| ④ | **点の順番のシャッフルに乱数の種がない** | 197 (`shuf`) | 順番は実行するたびに変わり、同じ順番は再現できない。【事実】実際の順番はログ (`==== [cycN][×n台] 点 ====` の行) に残っているので、後から確かめることはできる |
| ⑤ | **イメージが固定されていない** | `k6-job.yaml:24` (`latest`), `grpc_lb_patch.py` (`Always`) | 同じタグでも中身が変わり得る。実験時のイメージの中身 (ダイジェスト) は記録されていない |
| ⑥ | **台数ブロックごとの立て直し + 慣らし** | 111–144 | 前のブロックの影響と、起動直後の余計な CPU を除いている |
| ⑦ | **冷却待ちと温度の記録はセンサが違う** | 148–150 / 181 | 冷却待ちは CPU のセンサ (coretemp) を見る。CSV の `temp_max_c` は全センサの窓の中での最大値。両者は比べられない。【事実】ログ上、実際に冷却で待ったのは 204 点中 11 点、合計 94 秒 |
| ⑧ | **CSV は追記** | `_write_mixpoint.py:86` | 同じファイルに 2 回実行すると混ざる。【事実】このログの START は 1 回だけなので、mix-cpu2 では混ざっていない |
| ⑨ | **条件の記録** | 79, 135–136 | START 行と deploy 行が、「実際に何が設定されたか」の唯一の証拠。実行したコマンドそのものは残っていない (§3) |
| ⑩ | **10 秒刻みの系列には値の落ち込みがある** (2026-10-29 追記) | 182 | 【事実】時刻ごとの「系列 ÷ 主データ」の中央値は 0.993〜0.997 で、主データは別の問い合わせとほぼ一致する。一方、系列には比 0.7 未満のサンプルが 1 台で 6%、2 台で 21% 混ざる。【推測】`rate[30s]` の窓が短く、取得間隔との兼ね合いで欠けや低い値が出ている。【事実】リポジトリ内の解析で系列を使うものはないので、今の結果への影響はない |

## 8. 理解しておくとよいシェルの構文・記号

| 構文 | 実際のコード | 意味 |
|---|---|---|
| `${A:-B}` | `CYCLES=${CYCLES:-3}` (44) | 変数 `CYCLES` が外から渡されていればその値、無ければ 3 |
| `${A-B}` (コロンなし) | `LIMIT_OVERRIDE=${LIMIT_OVERRIDE-"frontend=…"}` (53) | 未定義のときだけ既定値。**空文字を渡すと空のまま**になる (コメントの「空文字を渡すとマニフェストのまま」はこのため) |
| `$( … )` | `t_run=$(date +%s)` (166) | 中のコマンドを実行し、その出力を値にする。`date +%s` = 今の時刻を秒で |

## 9. このスクリプトが実験設計のどこまでを決めているか (2026-11-02 追記)

### 9.1 結論

**このスクリプトが決めているのは「実行の手順」まで。** 具体的には、次の 9 つ。

| 記号 | 実験設計の要素 |
|---|---|
| A | 独立変数 (振る条件) |
| B | 反復の回数 |
| C | 順序の割り付け |
| D | 時間の設計 |
| E | 負荷生成器の容量 |
| F | 固定する条件 (統制) |
| G | 環境のそろえ方 |
| H | 従属変数 (測るもの) |
| I | 記録 |

**決めていないもの**: 次の 4 つは、スクリプトの外で決まる (§9.3)。
- 値をなぜそう選んだか
- 測る対象のシステムの中身
- 「1 周」の中身
- 除外・推定・解釈

§9.2 の各行の見方:
- 「定義」= 値を決めている行
- 「使用」= その値が実際に効く行
- 「実際の値」= mix-cpu2 の START 行 (`data/results-mix-cpu2.log` 1 行目) またはログで確認した値

【事実】行番号はすべて `scripts/measure-mix-cpu.sh` (コミット `c4ce1d1`) のもの。
