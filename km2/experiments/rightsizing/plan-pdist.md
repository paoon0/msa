# 計画: 需要の形 P とワークロード成分から同居相手を選べるか (pdist)

作成 2026-10-13 (同日改訂: アヌビス点検を受けてペアと判定を変更)。**同居実験の結果を見る前にコミットする。** 解析の規則を後から変えたら、変更前の結果も併記する。

## 1. 問いと最終的な提案

分離測定で求めた各サービスの需要の形 P と、運用で想定する負荷の配合の範囲 (ワークロード成分) から、同居させたときに HPA の「引きずり」(片方の需要で Pod が増え、もう片方まで余分に複製される) が起きるかを事前に言い当てられるか。

修論で提案したい選び方 (ユーザ 2026-10-13):
- P の近さは、ペアだけでは決まらず、**どの配合の負荷が来るか (ワークロード成分) に依存する**。例: front+ad は買い寄りの配合で遠く (M=0.83)、見る寄りでは近い (0.23)。
- 引きずりは「想定する配合の範囲で、片方だけが台数の境目を上に越える」ときに起きる。近さ M だけでなく、離れる向きと負荷の高さが効く。
- よって **ワークロード成分と P の両方からペアを選ぶ**。

## 2. 近さの指標と事前予測 (固定)

- P_s(m) = D_s(m)/D_s(b50v150)。D = 1 台固定時の CPU [m] の 6 サイクル平均 (`results-mix-cpu2.csv`)。
- M_W = max over m∈W of |ln P_s(m) − ln P_t(m)|。W = 買い寄り (view/buy≤1) / 中間 / 見る寄り (>3) / 全域 (buy>0)。
- **事前予測**: `predict_pdist.py` → `predictions-pdist.csv` / `predictions-pdist.txt`。各点の実測平均 D と枠 r から HPA の判定則 (目標 70%、許容幅 ±10%、同居 Pod は 2 コンテナの希望の最大) を開始台数から固定点まで回し、(ペア, 点, 開始台数) ごとに「引きずりの有無・引きずられる側・Δn」を出す。
- 比較の単純な規則 R1 (pairval と同じ): 買う側 {checkout, payment, shipping, email} と見る側をまたぐ組で、buy=100 なら損あり。予測と R1 が食い違うセルは 4 つ (front+ad b50v300 開始1、front+cart b100v0 開始2、catalog+checkout / currency+checkout b50v300 開始2)。

| ペア | アーム | 区分 | M 全域 | 通信 | 予測される引きずり |
|---|---|---|---|---|---|
| front + catalog | pairsP3 | 近い | 0.03 | あり | なし |
| checkout + shipping | pairsP1 | 近い | 0.06 | あり | なし |
| catalog + reco | pairsP1 | 近い | 0.11 | あり | なし |
| front + cart | pairsP2 | 中間 | 0.28 | あり | b100v0 開始2 で front |
| currency + checkout | pairsP3 | 遠い | 0.77 | あり | b100v0 で currency / b50v300 開始2 で checkout (向きが反転) |
| catalog + checkout | pairsP2 | 遠い | 0.81 | あり | b100v0 で catalog / b50v300 開始2 で checkout (向きが反転) |
| front + ad | pairsP1 | **R1 と逆** (同じ見る側だが遠い) | 0.83 | あり | b50v300 開始1 で front |

全 7 組に通信がある (アヌビス指摘: 通信の有無と近さの交絡を避ける)。

## 3. 実験 (固定)

- アーム: `normal` / `pairsP1` (front+ad, checkout+shipping, catalog+reco) / `pairsP2` (front+cart, catalog+checkout) / `pairsP3` (front+catalog, currency+checkout)。マニフェスト `summer2026/manifests/pairsP{1,2,3}.yaml`。
- 枠: `rightsize-pdist.csv` = b50v150・1 台の実測平均 / 0.50 (全 10 サービス、redis-cart 50m)。基準点で全サービスの利用率が 50% に揃う。
- 点: b100v0 (買う方に偏る) / b50v150 (基準 = 対照) / b50v300 (見る方に偏る)。開始台数 1 と 2、点ごとにリセット。
- 3 サイクル。点 × 開始台数の順番はサイクルごとにシャッフル、アームの順番は回転。
- WARM 180 s / MEAS 240 s。HPA 目標 70%、コンテナ別、SU 30 s / SD 60 s、min 1 / max 8。limits 上書き frontend / catalog 3000m、ad 1000m。GRPC_LB=1。
- 各点の前に CPU 温度 70℃ 以下まで冷却待ち (最長 600 s)。

## 4. 判定 (固定)

- **台数** = 計測窓内の時系列 (15 s 間隔) の current_replicas の最頻値 (Deployment 単位)。
- **主判定 (同じ Pod の中で)**: 同居 Pod の各コンテナの利用率 u (hpa_util_pct) から、そのコンテナ単独での希望台数 = n_st (|u/70 − 1| ≤ 0.1) / ceil(n_st·u/70) をサンプルごとに出し、窓内の最頻値が n_st より小さいコンテナを「引きずられた」とする。Δn = n_st − その希望台数。
- **副判定 (分離との比較)**: 同じサイクル・点・開始台数の normal アームの台数 n_s, n_t と n_st から 損 = n_st(r_s + r_t) − (n_s·r_s + n_t·r_t)。負の損も平均に含める。normal 側の台数は 3 サイクルの分布も示す。
- **結果変数**: 引きずりの有無、引きずられた側、Δn。損 [m] は引きずられた側の枠の大きさでほぼ決まるので副次的に添える。
- **有効・無効**: 取りこぼし (窓) が目標周回数 × 240 s の 1% 超、Pending、Ready 落ちの回は印を付けて報告するが、主な集計は全部の回で行い、印付きを除いた集計も併記する。

## 5. 集計と結論の出し方 (固定)

- (ペア, 点, 開始台数) の 42 セルごとに 3 サイクルの多数決で「引きずりあり/なし」と引きずられた側を決め、予測 (`predictions-pdist.csv`) と R1 の的中率を並べる。特に R1 と食い違う 4 セルで予測が当たるか。
- 遠い 2 組で、b100v0 と b50v300 で引きずる側が入れ替わるか (ワークロード成分で向きが変わることの直接の証拠)。
- 近い 3 組で引きずりが起きないか。
- **b50v300 は境目に近い点**: 1 台時の利用率が front 0.74 / catalog 0.72 / reco 0.76 / currency 0.71 / cart 0.72 と、HPA が台数を変えない帯の上端 0.77 のすぐ下。近い組でも偶然で片方だけが越えうる (同居 Pod は最大を取るので越えやすい)。b50v300 のセルは別に集計し、「負荷が境目付近まで来ると P が近くても引きずりうる」(ライブ論文の frontend+catalog が buy100+view200〜300 で 7/20 引きずられたのと同じ現象) の観測として扱う。
- 基準点 b50v150 は対照: 全ペアで引きずりなしのはず。
- 統計: 解析の単位はペア (7 組)。18 回を合算した検定はしない (擬似反復)。数字はセル単位の記述と、組ごとの的中で示す。

## 6. 限界 (先に書いておく)

- ペアは事前シミュレーションを見て選んだ (同じ `results-mix-cpu2.csv` に依存)。予測表はこのコミットで固定する。
- 枠は基準点で全サービスを揃える置き方 1 通り。損が出るかは HPA の整数の算術でほぼ決まるので、実験で確かめるのは (a) 分離で測った P が同居後も保たれるか、(b) HPA が算術どおり動くか、(c) 境目付近の揺らぎ。
- front が 3 アームすべてに入り、同じアームの組は同じ実行を共有するので、7 組は独立ではない。
- 同居による通信 CPU の減少 (過去 catalog −1.7% など) は予測に入れていない。全組に通信があるので両群に同様に入るはずだが、量は組で違う。
- ad (Java) は負荷開始直後に一時的に跳ね上がる (pairval スモーク)。窓 (WARM 180 s 後) の台数で判定するので影響は小さいはずだが、front+ad の窓内の台数変化は別記する。

**追記 (2026-10-14 00:20、スモーク後・本走前):**
- スモーク (`summer2026/smoke/*smoke-pdist*`、3 アーム × b50v300 開始1、WARM30/MEAS60) で、全 Pod Ready、枠検査 OK、limits 上書き、冷却待ち、同居 Pod のコンテナ別利用率の記録を確認した。取りこぼし (窓) は購入 1 周のみ。
- **ad (Java) は起動直後の JIT で利用率が跳ね上がる** (front+ad Pod で ad 470% → front ごと 3 台)。新しい Pod も跳ねるので落ち着きにくい (pairval の normal でも ad は 1→5→8→3 台)。P は定常の需要しか表さないので、front+ad の引きずりは P ではなく起動の過渡で起きうる。
- ユーザ判断 (「そういうサービスもある」): **front+ad はそのまま測り、主集計 (§5) から外して別に報告する**。窓内の ad の台数・利用率の推移を示し、「定常の P では捉えられない過渡の引きずり」の観察とする。R1 と食い違う残りの 3 セル (front+cart b100v0 開始2、catalog+checkout / currency+checkout b50v300 開始2) を主な識別セルとする。
