## 1. 狙いどおり「需要のズレ」を作れた

normal の窓内実測(需要 = 利用率 × 台数、各サービスの枠を単位):

| サービス | 閲覧0 | 閲覧100 | 閲覧200 | 閲覧300 | 増加率 |
|---|---|---|---|---|---|
| **frontend** | 0.71 | 0.95 | 1.44 | **1.77** | **+149%** |
| **productcatalog** | 0.67 | 0.88 | 1.18 | **1.49** | **+122%** |
| **checkout** | 0.70 | 0.83 | 0.86 | **0.90** | **+29%** |
| **email** | 0.78 | 0.82 | 0.92 | **0.95** | **+22%** |

閲覧型は `GET /product/x` だけなので checkout / email には届かない。
**frontend が2.5倍になる横で checkout / email は1.3倍しか動かない**。単一の枠設定では両方の比率で同時に揃えられない、という当初の狙いが数字で成立した。

## 2. ★主結果: 損の向きが閲覧比率で反転する

帰属方式(候補4サービスだけの予約枠)。**3サイクルすべて一致した帯だけを載せる**(閲覧100/200 は下記の理由で使えない)。

### 閲覧0(購入型のみ)— 冷たいはずの email が「熱い側」

normal の必要台数: frontend **1** / catalog **1** / checkout **1** / email **2**

| アーム | Δ予約枠 | 再現性 | 何が起きたか |
|---|---|---|---|
| **frontemail** | **+1077m** | **3/3** | email が2台必要 → **frontend が1→2台に引きずられた**。frontend コンテナは2台で36%(半分空き) |
| checkoutemail | +321m | 3/3 | email 2台 → checkout が1→2台に引きずられた |
| frontcheckout | 0 / 0 / +1398 | 2/3 | frontend 1台・checkout 1台で一致(3回目のみ両方2台に) |
| **catalogcheckout** | **0m** | **3/3** | catalog 1台・checkout 1台で**必要台数が一致** |

### 閲覧300 — 立場が入れ替わり、frontend が「熱い側」

normal の必要台数: frontend **3** / catalog **2** / checkout **2** / email **2**

| アーム | Δ予約枠 | 再現性 | 何が起きたか |
|---|---|---|---|
| **frontcheckout** | **+321m** | **3/3** | frontend 3台 → **checkout が2→3台に引きずられた** |
| **frontemail** | **+119m** | **3/3** | frontend 3台 → **email が2→3台に引きずられた** |
| checkoutemail | +662 / 0 / +662 | 2/3 | catalog の台数ゆらぎが混入(束ねとは無関係) |
| **catalogcheckout** | **0m** | **3/3** | catalog 2台・checkout 2台で**一致** |

### ここが今回いちばん重要

**同じ frontemail が、閲覧0では +1077m、閲覧300では +119m の損を出した。**
損の大きさが9倍違うのは、**引きずる側と引きずられる側が入れ替わった**から:

- 閲覧0: email(枠119m)が2台必要 → frontend(枠**1077m**)が引き上げられる → 損 = 1077m
- 閲覧300: frontend(枠1077m)が3台必要 → email(枠**119m**)が引き上げられる → 損 = 119m

**損 = (引きずられた側の枠) × (余分な台数)** という 8/19 に立てた式が、**両方向で当たった**。
枠の大小は「損の量」を決めるが、「どちらが引きずられるか」は需要の比率が決める。
⇒ **同じ束ねでも、ワークロードの比率が変われば損は1桁変わる。**

### catalogcheckout は全帯で損ゼロ
catalog と checkout の必要台数は閲覧0で1台・閲覧300で2台と**常に一致**した。
設計則「**必要台数が一致する相手と束ねよ**」の、これまでで最も直接的な確認。

## 3. 便益(softirq): エッジのない frontemail だけが正確にゼロ

1万リクエストあたりの softirq CPU(秒)、normal 比。**閲覧0(全点健全)**:

| アーム | softirq | normal比 | 取り込むエッジ |
|---|---|---|---|
| normal | 27.60 | — | — |
| **frontemail** | **27.67 ± 0.13** | **+0.2%** | **なし** |
| frontcheckout | 27.30 ± 0.14 | −1.1% | frontend→checkout |
| checkoutemail | 27.28 ± 0.34 | −1.2% | checkout→email |
| catalogcheckout | 27.21 ± 0.32 | −1.4% | checkout→catalog |

**エッジを取り込まない frontemail だけが、ばらつき(±0.13)の中でぴったりゼロ**。
残り3本は −1.1〜−1.4% の削減。ただし frontcatalog の **−16〜19%**(実験9/4)と比べると1桁小さい。
理由は明快で、これらのエッジは**購入1周につき1回**しか呼ばれないのに対し、
frontend→catalog は閲覧1回ごとに呼ばれるため通信量が桁違いだから。

⇒ **便益 = 取り込んだエッジの通信量**という主張の、対照実験による裏付け(ゼロの対照が取れた)。

## 4. 使えなかった帯(閲覧100 / 200)

- **閲覧100**: checkout の需要が 0.83 で **1台と2台のちょうど境界**。normal だけが cyc2/3 で1台に落ち、
  4アームすべてが一律 **+321m** に見える。これは束ねと無関係な**基準側のコイン投げ**。
- **閲覧200**: frontend の需要 1.44 が **2台と3台の境界**。加えて全アームで取りこぼしと遅延の跳ね上がりが発生
  (catalogcheckout cyc3 で p50 999ms 等)。CPU時間・softirq の比較も成立しない。

閲覧300 でも取りこぼしは出ている(normal cyc2 で購入477件・p50 1660ms)。
**予約枠(台数)は3サイクル一致していて堅いが、CPU時間の比較は閲覧0と100に限るべき。**

## 6. まとめ

1. **需要のズレは作れた**(frontend +149% vs checkout +29% / email +22%)。
2. **損の向きが反転することを実測した**。frontemail は閲覧0で +1077m、閲覧300で +119m。
   **損 = 引きずられた側の枠 × 余分な台数**が両方向で成立。
3. **必要台数が一致する catalogcheckout は全帯で損ゼロ**(3/3 × 2帯)。
4. **エッジを取り込まない frontemail の softirq 削減は +0.2%±0.13 = ゼロ**。便益項のゼロ対照が取れた。
5. 便益は細いエッジでは −1.1〜−1.4% にとどまる(frontend→catalog の −16〜19% とは1桁違う)。

⇒ **束ねの正味の得は「エッジの太さ」と「必要台数の一致」の両方が要る**。
frontemail は両方を欠く(得ゼロ・損最大)、catalogcheckout は両方を満たす(得あり・損ゼロ)。

## 7. 次にやるなら

- **閲覧比率を細かく刻む**(0/25/50/75/100)。今回 frontemail の損が 1077m → 119m と反転したので、
  **その間に損ゼロの点がある**はず。そこが「この束ねが成立するワークロード比率」の境界になる。
- **閲覧100/200 の境界問題を消す**には枠を1/3にする(9/4 の手法)。台数が3倍になり境界のコイン投げが減る。
