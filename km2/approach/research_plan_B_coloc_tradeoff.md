# 研究計画 — Pod 集約と独立スケールのトレードオフ（案B）

> 初学者向けに、専門用語にはそのつど補足を入れて書いています。
> 関連: `related_work.md`（先行研究）、`scaling/`（実験マニフェスト）。

---

## 0. ひとことで言うと

**「2つのマイクロサービスを 1 つの Pod にまとめるべきか、別々の Pod に分けるべきか」を、
2サービスの負荷の相関から計算で判断できるようにする** 研究です。

---

## 1. 背景と問題意識

### 1.1 用語の準備（最初に押さえる言葉）

- **マイクロサービス**: 1つの大きなアプリを、機能ごとの小さなサービスに分けたもの。本研究では Online Boutique（11個のサービスからなる EC デモ）を使う。
- **Pod**: Kubernetes が管理する最小の実行単位。中に1個以上のコンテナ（サービス）を入れられる。
- **スケール / レプリカ**: アクセスが増えたら同じ Pod のコピー（レプリカ）を増やして捌くこと。
- **HPA (Horizontal Pod Autoscaler)**: CPU 使用率を見てレプリカ数を自動で増減する仕組み。
- **相関 ρ（ロー）**: 2つのサービスの「混む時間帯」がどれだけ一致しているか。
  - 山が同じタイミング → ρ ≈ +1（正の相関）
  - 山が逆 → ρ ≈ −1（反相関）

### 1.2 何が問題か

サービスを **どれくらい細かく分けるか（粒度）** は、今は設計者の勘で決まっている。
先行研究を調べたところ、**「粒度を決めるコストと利益を動的に評価する手法」は空白**だった（`related_work.md`）。

2つのサービスをまとめる／分ける、それぞれに良し悪しがある：

| | 分離（1 Pod 1 サービス） | 集約（2 サービスを 1 Pod） |
|---|---|---|
| 良い点 | サービス毎に**独立にレプリカを増やせる**（必要な分だけ） | 固定費（後述）が減る |
| 悪い点 | サービスごとに固定費がかかる | Pod 単位でしか増やせない＝**片方だけ混んでも両方増える** |

集約の悪い点を **「レプリカ結合の無駄」** と呼ぶ。
片方のサービスだけ忙しいのに、まとめてあるせいで暇な相方も一緒にコピーされてしまう無駄。
この無駄は **2サービスの負荷の山がズレているほど大きい**。

### 1.3 本研究の新しさ（ここが主張）

仮想マシン（VM）統合の世界の常識は **「反相関のものを同居させてピークを均す」**。
ところが Pod 集約では独立スケールができないので、その常識が **逆転** する：

> **Pod 集約では「相関した（山が揃った）サービス」を同居させるべき。**

この「相関の好みが反転する」現象を、実機で測って数式の判断ルールにするのが新規性。

## 2. 理論モデル（判断の式）

2サービス A, B が時刻 t で必要とするレプリカ数を a(t), b(t) とする。

```
ΔC = (f·S − g·M)   −   r · ∫|a(t) − b(t)| dt
       静的メリット        動的な無駄
```

- 左の項（静的メリット）: 固定費の節約。`f`=分離時のPod1個あたり固定費、`g`=同居時の固定費。
  `g < 2f` なら同居でトクをする（Pod が1個減る、サイドカーが2→1になる等）。
- 右の項（動的な無駄）: **レプリカ結合の無駄。ちょうど ∫|a−b|（=必要数のズレの累積）**。`r`=レプリカ1枚の単価。

**集約が得 ⇔ ΔC > 0。**

ズレは相関を使うと `∫|a−b| ∝ σ√(1−ρ)`（σ=負荷の揺れの大きさ）と書けるので、
ΔC = 0 を解くと **集約すべきかの境目 τ（しきい値）** が出る：

> **ρ > τ なら集約、ρ < τ なら分離。**

### 重要な発見：境目 τ が「無い」場合がある

τ が −1〜+1 の内側に入るとは限らない。3つのレジーム（状況）がある：

1. **τ が内側にある** → 相関しだいで答えが変わる ＝ **唯一おもしろい領域**
2. **常に分離が得**（静的メリットが小さい）
3. **常に集約が得**（静的メリットが大きい）

そして **今の環境（単一ノード・Istio 未注入）は静的メリット ≈ 0 なので②** に当たる。
→ **これまで何をやっても集約と分離で差が出なかったのは、理論的に必然だった。**

→ だから実験の主タスクは **τ を内側（①）に押し込む**こと。
具体的には Istio サイドカーを注入して静的メリット（固定費の差 f−g）を作り出す。

## 3. 実験計画

### 3.1 比較する2構成（A/B 対照実験）

| | 分離版 `scaling/separated/` | 集約版 `scaling/colocated/` |
|---|---|---|
| 配置 | 2サービスを別 Pod | 1 Pod 内に同居 |
| 通信 | Service DNS 経由 | `localhost` 経由 |
| スケール | サービス毎に独立 HPA | Pod 単位の結合 HPA |

### 3.2 ペアの選び方（重要な設計判断）

実験の生命線は **相関 ρ を −1〜+1 まで自由に動かせること**（でないと τ の反転を描けない）。
ρ を動かすレバーは **loadgenerator のフロー比率だけ**。
→ **call graph 上で互いに直接呼び合わない「遠い」2サービスを選ぶ。**

- ✅ 採用候補: **recommendationservice（閲覧 `index` で駆動）↔ paymentservice（購入 `checkout` で駆動）**
  - 閲覧と購入の比率を時間変化させれば、2サービスの負荷の位相を独立にズラせる ＝ ρ を掃引できる。
- ❌ 避ける: reco → catalog のような隣接ペア。reco を呼ぶと必ず catalog を叩くので ρ が +1 に固定され、測りたいズレが作れない。
- ❌ productcatalog はハブ（全フローが叩く）なので位相制御に不向き＝ペアから除外。

> 注意: 遠いペアは「localhost で通信ホップを削る」恩恵が無い（互いに通信しないため）。
> その代わり静的メリットは **Envoy サイドカーを 2→1 に減らす** ことで作る（Istio 注入）。

### 3.3 操作する変数（つまみ）

1. **需要相関 ρ** — locust の閲覧:購入比を周期的に変えて、2サービスの山を揃える/ズラす。
2. **静的メリット f−g** — `sidecar.istio.io/inject: "true"` で Envoy 税を載せる。
3. **負荷振幅 σ・レプリカ単価 r** — 資源を絞ったマシン（`kubernetes-manifests/`）や負荷の振り幅で調整。

### 3.4 測る指標

- **主指標**: 同じ SLO（性能目標）を満たすのに使った **総 CPU·時間（cores·秒）**。
  - Prometheus の `container_cpu_usage_seconds_total`（アプリCPU）と `node_cpu_seconds_total`（ノード全体）。
  - 負荷実行の **最後の安定した時間窓だけ** を事後に厳密計測（既存手法、メモ参照）。
- **読み取り方**: 横軸 ρ、縦軸 ΔC（= 分離 − 集約 の総CPU）をプロット。
  **符号が反転する点 = τ** を実測し、「相関が高いほど集約有利」という反転を示す。

### 3.5 コストの定義 ── 予約(requests) か 実使用(usage) か（重要）

レプリカ1枚のコストを **予約 CPU（`requests`）** で数えるか **実使用 CPU** で数えるかで、
集約の「無駄」が本物かどうか＝**結論（τ の存在）が逆転する**。明示が必須。

- **実使用で数えると**：集約で増えた暇な相方レプリカはほぼ 0 CPU → 無駄がほぼ無料 → 集約がほぼ常に勝つ。
- **予約で数えると**：暇でも `requests` は確保され続け、他に回せない → 本物の無駄 → 山がズレると集約は損。

**本研究は「予約(requests)」を主コストに採る。** 理由：
1. K8s は `Σrequests ≤ ノード容量` で**スケジュール**する＝確保して空いている CPU は他に回せない本物のムダ（資源効率＝「何台要るか」は usage でなく requests で決まる）。
2. **HPA 自身が requests 基準**（使用率 = usage ÷ requests）。モデルの主役 a(t),b(t)（レプリカ数）は requests に対して定義される。
3. 決定論的でノイズに強い（requests×レプリカ数はきれいに出る）。

> 主張は「**同じ SLO を満たすのに確保すべき資源量**」の比較であって、「焼いた CPU サイクル数」ではない。

**条件（妥当性の前提）:** `requests` が**右サイズ**であること（requests ≒ 目標使用率での実使用）。
歪んだ requests のままだと予約コストは水増しになり HPA も歪む → **較正フェーズ1で右サイズ化**して担保する。

**副指標として実使用も併測**：①忙しいコンテナが requests 近くまで使っているか（右サイズの検証）、
②「予約 − 実使用」のギャップ＝集約の無駄の"中身"の説明、に使う。

## 4. 結果の使い道（予測への一般化）

全ペアを実機で試すのは非現実的。代わりに **少数点で式を較正 → 残りは計算で予測** する。

式の入力 ρ, σ, (f−g), r は **集約せずに事前測定できる**：

| 入力 | 取得元（集約不要） |
|---|---|
| ρ, σ | Prometheus の、各サービスが独立に動いているときの負荷履歴 |
| f−g | Envoy / Pod の固定オーバーヘッドの定数 |
| r | マニフェストの `requests`（CPU 予約） |

**予測手順:**
1. 各サービスの需要時系列 `aᵢ(t) = リクエスト率 ÷ 1レプリカの容量` を取得
2. 全ペアの相関行列 ρ_ij と σ を計算
3. ペア毎の静的メリットを見積もる（隣接=通信削減＋サイドカー化 / 遠い=サイドカー化のみ）
4. 較正済みの式で **予測 ΔC** を計算
5. ΔC > 0 のペアを「集約推奨」としてランキング（=先行研究 Knapsack 配置の相関考慮版）

**実験の役割** は、この式の係数（g<2f の効き、r、∫|a−b| の予測）が実機と合うかの **検証**。
ρ の高いペアと低いペアの **最低2点** で曲線の形を確認してから外挿する。

**予測が外れる条件（正直な限界）:**
1. サービスごとに 1レプリカの容量 r が違う（例: email は Jinja2 レンダリングで重い）→ ∫|a−b| は容量で重みづけして測る
2. HPA はレプリカを整数に切り上げ＋ `minReplicas` の床がある → 低負荷域でモデルとズレる
3. 1点だけで外挿は危険。必ず2点で形を確認する

---

## 5. 進め方（マイルストーン）

1. **集約版マニフェストの実装** — `scaling/colocated/` を「reco + payment を**1 Pod に2コンテナ同居・Envoy 共有・結合HPA**」に書き換える。reco と payment は互いに通信しないため localhost 書き換えは不要（同居の狙いは Pod/Envoy 固定費の共有とスケールの結合）。
2. **負荷生成の位相制御** — locust の閲覧:購入比を時間で変えられるようにし、ρ を数水準（例 −0.8, 0, +0.8）作る。
3. **静的メリットの導入** — Istio 注入の ON/OFF で f−g を変える。
4. **計測** — 各 (構成 × ρ) を複数回反復し、総 CPU·時間を最後の安定窓で測る。
5. **τ の同定** — ΔC(ρ) をプロットし、符号反転点 τ を求める。
6. **予測モデルの検証** — 別ペアで予測 ΔC と実測を比較し、式の外挿が効くか確認。

## 6. 想定される貢献

- **設計判断ルール**: 「2サービスを1 Podにまとめるべきか」を相関から計算で決める枠組み（粒度設計の空白を埋める）。
- **常識の反転の実証**: VM統合の「反相関を同居」が、Pod集約では「相関を同居」に反転することを実機で定量化。
- **予測の枠組み**: 少数の較正点から、未試行ペアの集約可否をランキングできる。

> 範囲の正直な明示: 出るのは Online Boutique・単一ノードでの一事例。
> 価値は τ の数値そのものより、**静的×動的を束ねる式と相関反転の枠組み**にあり、こちらは他システムへ移植可能。

## 付録A：コストモデルを一から（初学者向け・数値例つき）

§2 の式を、具体的な数字で組み立て直す。式が苦手でも、**お話と表**で追えるようにする。

### A-0. 何を比べるのか

2サービス A・B を動かすのに **分離**（別 Pod・独立スケール）と **集約**（同居・Pod ごと一緒にスケール）の
どちらが CPU を食わないかを比べる。「コスト」＝ **予約した CPU 量 × 時間**（K8s は `requests` で CPU を確保するので、使わなくても確保分はコスト）。

### A-1. レプリカ1枚の値段 ＝「仕事」＋「税金」

レプリカ1枚には2種類の CPU がかかる。
- **仕事ぶん `r`**：本来の処理に使う予約（例: 100m）。
- **税金ぶん（固定費）**：処理と無関係に Pod を1つ立てるだけでかかる分（Pod 土台＋Envoy アイドル）。
  - `f` ＝ 分離時の Pod 1枚の税金（例: 50m）、`g` ＝ 集約時の Pod 1枚の税金（例: 60m）。
  - 集約 Pod は A・B が **Envoy を1枚共有**するので普通 **g < 2f**。これが集約のうれしさの源。

| | 中身 | CPU |
|---|---|---|
| 分離の A（または B）1枚 | 仕事 r ＋ 税金 f | 100+50 = **150m** |
| 集約 Pod 1枚 | A仕事 r ＋ B仕事 r ＋ 税金 g（共有） | 100+100+60 = **260m** |

### A-2. 時間で変わる必要レプリカ数（A=閲覧で朝に混む / B=決済で夜に混む）

| 時間帯 | a（A必要枚数） | b（B必要枚数） | a+b | max(a,b) | \|a−b\| |
|---|---|---|---|---|---|
| 朝 | 4 | 1 | 5 | 4 | 3 |
| 昼 | 2 | 2 | 4 | 2 | 0 |
| 夜 | 1 | 4 | 5 | 4 | 3 |
| 深夜 | 1 | 1 | 2 | 1 | 0 |
| **合計** | | | **S=16** | **M=11** | **W=6** |

- **S = Σ(a+b)** ＝ 全レプリカ数の合計、**M = Σmax(a,b)** ＝ 忙しい方の合計、**W = Σ\|a−b\|** ＝ 山のズレの合計。

### A-3. 2つの構成のコスト

- **分離** ＝ 必要な分だけ払う ＝ `S × (r+f)` = 16 × 150 = **2400**。
- **集約** ＝ 忙しい方に合わせて Pod を立てる（暇な相方も同数できる）＝ `M × (2r+g)` = 11 × 260 = **2860**。

> 朝の直感：A が4枚欲しい → 集約は Pod を4枚 → B のコンテナも4枚できるが B は1枚で足りる → **3枚がムダ**（＝レプリカ結合の無駄）。

```
ΔC = 分離 − 集約 = 2400 − 2860 = −460  （マイナス ＝ この場合は分離が正解）
```

### A-4. 差の中身 ＝ 2つの力の綱引き

```
ΔC = (f·S − g·M)   −   r·W
      静的メリット       動的な無駄
      （まとめたい力）     （分けたい力）
```

- **静的メリット** ＝ `f·S − g·M`：分離は全レプリカに税金 f、集約は Pod 数 ぶんだけ税金 g（共有で安い）。
  = 50×16 − 60×11 = 800 − 660 = **140**。
- **動的な無駄** ＝ `r·W`：暇な方を忙しい方の枚数に合わせるムダ。差 \|a−b\| のぶん仕事 r が無駄。
  = 100×6 = **600**。
- 合計 ΔC = 140 − 600 = **−460**（A-3 と一致）。

### A-5. 山が「揃う」と結果が反転する

同じ2サービスでも負荷の山が揃う（相関が高い）と W=0：

| 時間帯 | a | b | \|a−b\| |
|---|---|---|---|
| 朝 | 4 | 4 | 0 |
| 昼 | 2 | 2 | 0 |
| 夜 | 3 | 3 | 0 |
| 深夜 | 1 | 1 | 0 |

S=20, M=10, W=0 → 静的=50×20−60×10=400、動的=0 → **ΔC=+400（集約が正解）**。

> **結論：同じサービスでも、山がズレてる（反相関）→ 集約は損、揃ってる（相関）→ 集約が得。**
> だから「まとめるべきか」は負荷の相関 ρ で決まる。

### A-6. ∫ と τ の補足

- 式の **∫\|a−b\| dt** は「各時間帯の \|a−b\| を全部足す」＝ 上の **W**。`∫`＝「時間で足し合わせる」記号。
- 相関 ρ が高いほど W は小さい（`W ∝ √(1−ρ)`）。ΔC=0 になる ρ が **しきい値 τ**。**ρ>τ で集約、ρ<τ で分離**。
- §2 の「τ が無い3レジーム」＝ 静的メリットが小さすぎ/大きすぎると、どんな ρ でも片方が常勝して境目が現れない状態。

### A-7. HPA が多数レプリカに増える件（ContainerResource 反論への答え）

- a(t), b(t) は1枚ではなく **HPA が増やした必要枚数（0〜maxReplicas）**。集約 Pod 数 = max(a,b) なので「多数に増える」状況はモデルに織り込み済みで、無駄 W はレプリカが増えるほど育つ。
- v1.30 の **ContainerResource HPA** は「**何を引き金にスケールするか**（=忙しいコンテナ）」を変えるだけで、「**複製の単位が Pod**」である事実は変えない。Pod を増やせば両コンテナが必ず複製される → **無駄 W は構造的に残る**。これを実証するのが新規性。
- 実装：集約版 HPA に **ContainerResource を2本**（reco 用・payment 用）並べると、HPA は各メトリクスの最大を採るので **desired = max(a,b)** を素直に実現できる。
