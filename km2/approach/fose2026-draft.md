## 題目

**オートスケール環境におけるマイクロサービスの部分集約 —— 効果と相手選びの2軸**

別案: 「オートスケーラを考慮した部分集約の適用条件」

---

## 概要

マイクロサービスを細分化すると、サービス間通信がすべてネットワークを経由し、かつオートスケーラがサービスごとに独立して台数を決める。複数サービスを1つの Pod に同居させる**部分集約**はこの両方に影響するが、既存研究は Kubernetes のオートスケール環境を対象としていない。本稿では、Online Boutique を用いた実機実験により、(1) 部分集約が Kubernetes 環境でも容量を改善すること、(2) その効果が組み合わせに強く依存し、必要台数が揃わない相手を選ぶと予約資源が最大18%増加すること、(3) 相手選びには「通信量」と「ワークロード成分」という独立な2軸が必要であることを示す。

---

## 1. はじめに

マイクロサービスアーキテクチャでは、サービスをどの粒度に分割するかが設計上の主要な判断となる。細分化は独立したデプロイやスケーリングを可能にする一方、二つの代償を伴う。第一に、サービス間の呼び出しがすべてネットワークスタックを経由するため、通信処理のオーバーヘッドが生じる。第二に、Kubernetes の水平オートスケーラ (HPA) がサービスごとに独立して台数を決めるため、実際の需要より粗い粒度でしか資源を割り当てられない。

これに対し、直接通信する複数のサービスを1つの Pod 内に同居させ、通信を localhost 経由にする**部分集約**が考えられる。Wickramanayaka ら [1] は Docker Swarm 環境で、通信量の多いコンテナを同一ホストに配置・統合することで通信量が最大58.5%減少することを示した。Alvaro ら [2] は、マイクロサービスでは CPU サイクルの25〜40%しか業務ロジックに使われず、残りが通信処理に費やされることを報告している。

しかし、これらはいずれも **Kubernetes のオートスケール環境を対象としていない**。オートスケーラが台数を決める環境では、部分集約は通信を減らす一方で「Pod を分割できない」という新たな制約を持ち込む。本稿では、部分集約が Kubernetes 環境でも効果を持つことを確認したうえで、その効果が組み合わせに強く依存することと、相手選びに必要な判断軸を示す。

---

## 2. 部分集約とオートスケーラの干渉

HPA は Deployment 単位で台数を決める。複数のサービスを1つの Pod に同居させると、**それらは同じ台数でしか複製できない**。したがって同居した Pod の台数は、各コンテナが必要とする台数の最大値になる。

サービス s の枠 (requests) を r(s)、単独で必要な台数を n(s)、同居した Pod の台数を

```
    N = max n(s)          … 集約対象の中での最大
```

とすると、部分集約によって余分に確保される資源は

```
    Δ = Σ ( N − n(s) ) × r(s)        … 式(1)
        s
```

となる。すなわち**損は「引きずられた側の枠」に比例**し、誤差を出した側の枠には依存しない。必要台数が揃えば Δ = 0 である。

以降、この Δ を**粒度損**と呼び、部分集約の主要なコストとして扱う。

---

## 3. 実験環境

対象は Google の Online Boutique(11サービス、gRPC 通信)である。MicroK8s(単一ノード、16コア)上にデプロイし、負荷は k6 の開ループ (constant-arrival-rate) で与えた。HPA はコンテナ単位のメトリクス (ContainerResource) を用い、目標利用率70%、増加の様子見30秒・減少60秒とした。

枠 (requests) はマニフェストの既定値ではなく、実測から適正化した。各サービスを1台に固定し HPA を切った状態で負荷を6段階(10〜150周/秒)与え、CPU 使用量を負荷の1次式として最小二乗法で近似し、

```
    枠 = ( アイドル分 + 1リクエストあたりCPU時間 × k ) ÷ 0.7      … 式(2)
                                              k = 100 周/秒
```

とした。これにより、理想的には全サービスが同じ負荷で目標利用率に到達し、必要台数が一致する。

評価指標は、粒度損として**予約枠**(稼働 Pod の requests 合計)、通信コストとして **softirq モードの CPU 時間**(cgroup の外で消費されるため HPA には見えない)を用いた。さらに、各 Pod のネットワーク名前空間から `ss -tin` を読み、サービスペアごとの通信量を実測した。

---

## 4. 予備実験: Kubernetes 環境での効果

まず、部分集約が Kubernetes 環境で効果を持つかを確認した。frontend・recommendation・productcatalog の3サービスを1 Pod に同居させた構成と、1 Pod 1 サービスの分離構成を比較した(3回反復)。

**表1 部分集約の効果(負荷 users = 240、3回平均)**

| 構成 | スループット [req/s] | softirq [mCPU/req] | Pod 数 |
|---|---|---|---|
| 分離 | 639.2 ± 32.5 | 0.932 | 18.3 |
| **部分集約** | **704.7 ± 5.9** | **0.632** | **14.3** |
| 差 | **+10.2%** | **−32%** | **−22%** |

部分集約は**より少ない Pod でより多くのリクエストを処理**した。3回すべてで集約が上回り、ばらつきも約1/5に小さい。通信コストは32%削減されている。Kubernetes 環境でも部分集約が有効であることを確認できた。

---

## 5. 効果は組み合わせに依存する

一方で、部分集約の効果は相手の選び方に強く依存する。以下では frontend と emailservice を同居させた構成(以下 FE+email)を例に示す。frontend は emailservice を呼び出さないため、この組み合わせには**通信削減の効果がない**。実際、softirq の削減は +0.2 ± 0.13% と、ばらつきの範囲でゼロであった。

### 5.1 枠の調整で消える損

購入型の負荷のみを与え、レートを変えて粒度損を測った。

**表2 負荷レートと粒度損(3サイクル)**

| 購入レート | 必要台数(frontend / email) | FE+email の粒度損 |
|---|---|---|
| 100 周/秒 | 1 / **2** | **+1077 mCPU**(3/3) |
| 150 周/秒 | 2 / 2 | **0**(3/3) |

100周/秒 では emailservice のみ2台を要し、同居する frontend(枠 1077 mCPU)が引きずられて1台分まるごとが無駄になった。予約枠は全体で18%増加した。ただし emailservice は1台のとき利用率83%であり、増設ラインである77%をわずかに超えたにすぎない。**枠を7%大きくしていればこの損は生じなかった**。実際 150周/秒 では両者とも2台となり、損は消える。この帯では他の3つの組み合わせでも粒度損はゼロであった。

すなわちこの損は**枠の測定精度に起因し、原理的には除去できる**。

### 5.2 枠の調整では消えない損

次に、閲覧型の負荷(商品ページの閲覧のみ)を加えた。閲覧型は checkout や email を呼び出さないため、サービスごとに負荷の増え方が異なる。実測では、閲覧型を0から300周/秒 に増やすと **frontend の需要は2.5倍**になる一方、**emailservice は1.2倍**にしかならなかった。

**表3 ワークロード比率と粒度損の反転(3サイクル、いずれも3/3で一致)**

| 閲覧レート | 必要台数(frontend / email) | 引きずられる側 | 粒度損 |
|---|---|---|---|
| 0 | **1** / **2** | frontend(枠 1077 m) | **+1077 mCPU** |
| 300 周/秒 | **3** / 2 | email(枠 119 m) | **+119 mCPU** |

**同じ組み合わせでありながら、引きずる側と引きずられる側が入れ替わり、損が9倍変化した**。損の比 1077 ÷ 119 = 9.05 は枠の比と一致し、式(1)が両方向で成立している。

さらに、この2つの条件で同時に損をゼロにする枠は**存在しない**。emailservice の枠を r [mCPU] とすると

```
    閲覧0   で1台に収める条件 :  93 ÷ r ≤ 0.77        →  r ≥ 121
    閲覧300 で3台にする条件   : 113 ÷ (2 × r) > 0.77  →  r <  73
```

であり、両立しない。枠は各サービスに1つしか与えられないのに対し、需要の比はワークロードの混合比によって変化するためである。**この損は枠の調整では原理的に除去できない**。

対照として、productcatalog と checkout を同居させた構成では、全ワークロード比率で必要台数が一致し、粒度損は常にゼロであった。

### 5.3 通信量とワークロード成分は独立な軸

部分集約の相手は通常、通信量の多いサービスから選ばれる。そこで各エッジの通信量を実測し、ワークロード成分(閲覧型が到達するか否か)で分類した。

**表4 エッジの通信量と成分(購入1周あたり、上位のみ)**

| エッジ | 通信量 [B] | シェア | 成分 |
|---|---|---|---|
| frontend ↔ productcatalog | 5410 | 34.4% | 同一 |
| productcatalog ↔ recommendation | 4428 | 28.1% | 同一 |
| currency ↔ frontend | 1231 | 7.8% | 同一 |
| **frontend ↔ checkout** | 407 | **2.6%** | **異なる** |
| **cart ↔ checkout** | 345 | 2.2% | **異なる** |

本アプリケーションでは、**成分をまたぐエッジは5本、通信量の 9.6% にすぎず、最も太いものでも 2.6%** であった。逆に同一成分のエッジが 90.4% を占める。

これは偶然ではない。エッジの太さは呼び出し回数で決まり、回数はそのエッジを通るワークロード成分の量で決まる。したがって**太いエッジは頻度の高い経路の上にあり、その経路上のエッジは両端とも同じ成分で駆動される**。成分をまたぐのは経路が切り替わる箇所のみであり、構造的に細くなる。

---

## 6. 考察と今後の課題

以上より、部分集約の相手選びには2つの独立な軸が必要である。

- **通信量**: 大きいほど便益が大きい。枠の設定とは無関係であり、実際、枠を3倍変えても softirq の削減率は 16.4% と 16.2% でほぼ変化しなかった。
- **ワークロード成分**: 異なる相手を選ぶと、枠の調整では除去できない粒度損が生じる。

**最も危険なのは「通信量が多く、かつ成分が異なる」組み合わせ**である。通信量だけで相手を選ぶ従来の方針では、この組み合わせを避けられない。本実験環境ではこの象限が空であったため両者は衝突しなかったが、これは上記の構造的理由による。非同期処理やバッチ処理など**別系統のワークロードを持つアプリケーションではこの前提が崩れる**と考えられ、Sock Shop のようにメッセージキューを含む構成での検証が今後の課題である。

また、本実験は単一ノードで行っており、ノードをまたぐ通信(overlay ネットワーク)を含まない。先行研究 [1] が示した効果の大部分は overlay の有無に由来するため、マルチノード環境では便益がさらに大きくなると予想される。
